# 10. Configuration and custom builds

`dist/layout.css` is generated by a small builder from a config file,
[`layout.config.json`](../layout.config.json). The default config includes every layout at
the breakpoints where it makes sense, and the full spacing scale at `xs` and `lg`, so the
demos and a quick start work out of the box.

A real site uses far less than that. Every layout × breakpoint and every
spacing token × size × breakpoint is a CSS rule, so a config that lists only what the site
uses produces a much smaller stylesheet. On a realistic 30-section test page, the trimmed
file was about a third of the full one (17 KB instead of 49 KB minified), and it rendered
no slower.

## Building your own

Put a `layout.config.json` in your project and run the builder from the installed package:

```bash
npx browser-style-layout --config ./layout.config.json --output ./dist/layout.css
```

Or from JavaScript:

```js
import { buildLayout } from '@browser.style/layout/builder'
await buildLayout({ configPath: './layout.config.json', outputPath: './dist/layout.css' })
```

Your config doesn't need copies of the package's `core/` or `layouts/` folders. The builder
uses the package's own unless you put folders with those names next to your config. A
minified `layout.min.css` is written too when `postcss` and `cssnano` are installed in your
project.

## The config, section by section

```json
{
  "element": "lay-out",
  "layoutContainer": { "element": "body", "maxWidth": 1024, "margin": "1rem" },
  "core": ["base", "group"],
  "common": ["animations"],
  "spacing": { … },
  "breakpoints": { … }
}
```

| Key | What it sets |
|---|---|
| `element` | The element name, `lay-out` by default |
| `layoutContainer` | The page column: `maxWidth` becomes `--layout-bleed-mw` and `margin` becomes `--layout-mi` |
| `core` / `common` | Static CSS files to include: `base` (the engine), `group` (`<lay-out-group>`) and `animations` (`stack(reveal)`) |
| `spacing` | Which spacing tokens and sizes to generate, and at which breakpoints |
| `breakpoints` | The breakpoints, their widths, and the layouts at each one |

### Breakpoints and layouts

```json
"breakpoints": {
  "xs":  { "type": "@media", "srcsetMin": "240px", "layouts": ["stack"] },
  "md":  { "type": "@media", "min": "540px", "layouts": ["columns", { "grid": ["grid(3a)"] }] },
  "lg":  { "type": "@media", "min": "720px", "layouts": [{ "bento": ["bento(6a)"], "ratios": ["ratio(33:66)"] }] }
}
```

- **A breakpoint without `min`** is the mobile-first base, and its rules apply at every
  width. Give it a `srcsetMin` so the responsive-image helpers know its width.
- **A family name as a string** (`"columns"`) includes every variant of that family.
- **An object** picks single variants: `{ "grid": ["grid(3a)"] }`. The key is the layout
  file's name (`asymmetrical`, `autofit`, `ratios`, `bento` …) and the values are the tokens
  as you write them in HTML (`asym(l-r)`, `auto(fit)`, `ratio(33:66)`).
- Keep `stack` at your base breakpoint: it's small, and other features build on it.

### Spacing

```json
"spacing": {
  "steps": [0, 0.75, 1, 2, 3, 4,
    { "label": "3xs", "value": 0.0625 }, { "label": "2xs", "value": 0.125 },
    { "label": "xs", "value": 0.25 },   { "label": "sm", "value": 0.5 },
    { "label": "md", "value": 1 },      { "label": "lg", "value": 1.5 },
    { "label": "xl", "value": 2 },      { "label": "2xl", "value": 3 }],
  "tokens": ["p", "pi", "pb", "pbs", "pbe", "mbs", "mbe", "cg", "rg"],
  "breakpoints": ["xs", "lg"]
}
```

| Key | Meaning |
|---|---|
| `steps` | The scale: every size a token can take. A number is its own multiplier; `{ "label", "value" }` gives a size word its multiplier |
| `tokens` | Which tokens to generate (see the two forms below) |
| `breakpoints` | Optional: generate spacing only at these breakpoints. Leave it out for all of them |
| `nest` | Optional, `true` by default: write each breakpoint's spacing rules nested under one parent selector. It's about 13% smaller and behaves the same. `false` writes flat selectors |

`tokens` comes in two forms:

**A list of names** generates every step in `steps` for each token:

```json
"tokens": ["p", "cg", "rg"]
```

**An object** lists the steps each token needs, by label or by number. `"*"` means every
step:

```json
"tokens": { "cg": ["sm", 2], "rg": ["sm"], "pb": [1, 3], "p": "*" }
```

The object form is how a site build stays small. Spacing is roughly 40% of the generated
CSS, and most sites use only a few sizes per token. A step you name must exist in `steps`,
because that's where a size word gets its value. The builder warns about an unknown step
and skips it.

Any breakpoint can override `tokens` with its own `spacing`, in either form. `[]` turns
spacing off at that breakpoint:

```json
"breakpoints": {
  "xs": { "layouts": ["stack"], "spacing": { "pi": [1], "pb": [1, 3] } },
  "lg": { "min": "720px", "layouts": ["columns"], "spacing": { "cg": [2], "pb": [3] } }
}
```

## Checking your markup against the build

A token that isn't in your build isn't an error in the browser: it just does nothing.
`--check` makes those visible. It builds as usual, reads the breakpoint attributes of every
`<lay-out>` and `<lay-out-group>` in the files you give it, and lists each token the build
has no rule for:

```bash
npx browser-style-layout --config ./layout.config.json --output ./dist/layout.css --check ./pages/*.html
```

```
⚠ xl="grid(3c)" is used 1× but not in this build: it does nothing in the browser
    ./pages/index.html
⚠ xs="pbe(6)" is used 1× but not in this build: it does nothing in the browser
    ./pages/index.html

2 token(s) missing from layout.config
```

- **HTML files** are scanned for `<lay-out>` and `<lay-out-group>` start tags.
- **A `.json` file** is an array of attribute objects, which is easy to export from a CMS:
  `[{ "md": "columns(2) cg(sm)", "lg": "bento(6a)" }]`.
- The command exits with code 1 when something is missing, so it can run in CI.
- Put `--check` and its files last on the command line.

What a missing token means for the page: at that breakpoint the element keeps the layout
and spacing it had at the smaller breakpoints. Either add the token to the config, or fix
the markup if it's a typo (`pbe(6)` above isn't on the scale at all).

## Generating the config from a CMS

If your content comes from a CMS that stores layout attributes, you can generate the config
from that content:

1. Collect every stored attribute object (`{ xs, sm, md, lg, xl, xxl }`).
2. Split each value on spaces. Add each layout token to that breakpoint's `layouts`, under
   its family's file name, and each spacing token's size to that breakpoint's `spacing`.
3. Set `spacing.breakpoints` to the breakpoints that have spacing, and `spacing.tokens` to
   `[]`.
4. Build with `--check` against the same attribute objects. A clean check means the
   generated CSS covers all the content.

## Adding your own layouts

A layout family is a JSON file in a `layouts/` folder next to your config. Each variant
gives the column template and, when needed, per-child rules:

```json
{
  "name": "Hero Layouts",
  "prefix": "hero",
  "layouts": [
    {
      "id": "1",
      "columns": "2fr 1fr",
      "items": 2,
      "srcset": "66.67%,33.33%",
      "rules": [{ "selector": ":nth-child(1)", "properties": { "--layout-ga": "span 2 / 1" } }]
    }
  ]
}
```

Reference it in a breakpoint (`{ "hero": ["hero(1)"] }`) and use it as `lg="hero(1)"`. The
repository's `create-layout` skill walks through the details, including icons and demo
pages.

## Version history

The per-token spacing steps, nesting, the narrower breakpoint reset and `--check` were added
in the 2.0 release of `@browser.style/layout`. A config written for an earlier version
builds unchanged.
